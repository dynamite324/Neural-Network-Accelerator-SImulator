# Neural Network Accelerator Simulator ⚡

A Python simulation that models how a hardware neural network accelerator (like a systolic array / MAC-unit array found in NPUs and TPUs) speeds up matrix multiplication compared to a naive CPU implementation — and explores how the number of parallel MAC (multiply-accumulate) units affects performance.

Originally built and run in Google Colab.

## Overview

Matrix multiplication is the core operation behind neural network inference and training. This notebook simulates two approaches to it:

1. **Naive CPU implementation** — a pure Python triple-nested loop, representing how matrix multiplication would run without any hardware acceleration or vectorization.
2. **Accelerator simulation** — a NumPy-vectorized implementation representing how a dedicated accelerator (with many parallel MAC units) would perform the same operation.

It then benchmarks both across increasing matrix sizes and simulates the effect of limiting the accelerator to a fixed number of parallel MAC units, mimicking real hardware constraints.

## Features

- **CPU baseline (`cpu_matrix_multiply`)** — a plain Python triple-loop matrix multiplication with timing.
- **Accelerator baseline (`accelerator_matrix_multiply`)** — a NumPy `np.dot`-based multiplication with timing, representing fully parallel hardware execution.
- **Correctness check** — verifies CPU and accelerator results match using `np.allclose`.
- **Performance benchmarking** — times both implementations across matrix sizes (50×50 up to 200×200) and plots execution time vs. matrix size.
- **Speedup calculation** — reports how many times faster the accelerator is than the CPU.
- **MAC-unit-limited simulation (`accelerator_with_mac_limit`)** — models a hardware accelerator with a *fixed* number of MAC units by processing output elements in batches, showing how parallelism (1, 2, 4, 8, 16 units) affects execution time.
- **Matrix input utilities** — helpers to read matrices interactively (`take_input_matrix`) or from a text file (`read_matrix_from_file`), plus a demo of writing/reading a sample `input.txt`.
- **Visualizations** — line plots comparing CPU vs. accelerator time, and a plot showing how execution time drops as MAC unit count increases.

## How It Works

### 1. CPU vs. Accelerator Benchmark
- `generate_matrix(size)` creates random `size × size` integer matrices.
- `cpu_matrix_multiply` runs the classic O(n³) triple-loop multiplication in pure Python.
- `accelerator_matrix_multiply` runs the same multiplication via `np.dot`, standing in for a hardware accelerator that performs many MACs per cycle in parallel.
- Both are timed and compared, reporting a speedup ratio (accelerator time is typically orders of magnitude faster, illustrating the benefit of dedicated hardware/vectorized execution).

### 2. Scaling Study
- The benchmark is repeated across matrix sizes `[50, 100, 150, 200]`.
- Results are plotted to show how CPU time grows much faster than accelerator time as matrix size increases — a proxy for why dedicated accelerators matter more as models/workloads scale up.

### 3. Correctness Verification
- `np.allclose` confirms the CPU and accelerator implementations produce numerically equivalent results, so the speedup isn't coming from a shortcut that changes the answer.

### 4. Modeling Limited Parallelism
- Real accelerators have a *finite* number of MAC units, not infinite parallelism.
- `accelerator_with_mac_limit(A, B, mac_units)` simulates this by splitting the `(i, j)` output positions into batches of size `mac_units` and processing one batch at a time (still using NumPy per-element `np.dot`, but throttled by batch size).
- Running this with `mac_units = [1, 2, 4, 8, 16]` shows how execution time decreases as more MAC units are simulated — a simplified illustration of the parallelism/throughput tradeoff in accelerator design.

### 5. Matrix I/O Utilities
- `take_input_matrix()` lets a user type in a matrix interactively.
- `read_matrix_from_file(filename)` reads two matrices (A and B) from a structured text file, where line 1 is the size `n`, followed by `n` rows for A and `n` rows for B.

## Getting Started

### Prerequisites
```bash
pip install numpy matplotlib
```

### Running the Notebook
Run the cells top to bottom in Jupyter, Colab, or any notebook environment. No external datasets or credentials are required — everything is generated locally (random matrices, or the sample `input.txt`).

### Example: Running a Custom Benchmark
```python
size = 300
A = generate_matrix(size)
B = generate_matrix(size)

cpu_result, cpu_time = cpu_matrix_multiply(A.tolist(), B.tolist())
acc_result, acc_time = accelerator_matrix_multiply(A, B)

print(f"CPU Time: {cpu_time:.4f}s, Accelerator Time: {acc_time:.4f}s")
print(f"Speedup: {cpu_time / acc_time:.2f}x")
```

### Example: Simulating MAC Unit Scaling
```python
mac_units_list = [1, 2, 4, 8, 16, 32]
times = [accelerator_with_mac_limit(A, B, mac_units=m)[1] for m in mac_units_list]
```

## Future Improvements

- Replace the pure-Python CPU loop with a NumPy-free-but-optimized baseline (e.g., using `array` module) for a fairer "software" comparison, since pure Python loops are unrealistically slow compared to any compiled CPU code.
- Extend `accelerator_with_mac_limit` to simulate a more realistic systolic array data flow (e.g., streaming rows/columns through a 2D grid of MAC units) rather than simple batching.
- Add memory bandwidth / data movement modeling, since real accelerator performance is often bottlenecked by data transfer, not just compute units.
- Parameterize and log results (matrix size, MAC units, time) to a table/CSV for easier comparison across many configurations.
- Add unit tests for `read_matrix_from_file` and `cpu_matrix_multiply` to guard against indexing bugs (the notebook already fixes one such bug for `read_matrix_from_file` inline — worth formalizing with a test).
